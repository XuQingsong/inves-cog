# M9 开发问题与保守处理

## K01｜现有 M8 完成标记与历史可见快照接口（仅真实适配/AC03受影响）

位置：M9 FR04、异常降级“当日M8未完成沿用上一版本”、AC03的五日PIT回放。现有perception.linkage_events保留当前lifecycle与history；reports/tracks是可更新的当前结果，并非每字段都有历史生成时间。

请需求方指出已验收M8中可直接复用的当日完成标记/job名，以及包含暴露、方向、机制、背离标签的按cutoff历史快照/导出入口。需要的是既有合同定位，不要求新生产权限、模型或补跑。最新可变report不能被当成五个过去交易日已经知道的结论。

处理：纯函数接收明确的source_events_asof与source_complete，并验证输入时点；真实适配缺标记时保留旧覆盖层generated_at、写degraded，不把“0事件/表可读”当作当日完成。不修改M8表/接口或借管理员读取。离线合成契约、golden和自己的schema可继续，真实五日回放若缺原快照则明确未证明；不阻塞不依赖该接口的M9开发。

## K02｜M4/M9发布时序及冬令时间合同（仅调度接线受影响）

位置：M9 FR04 / README §3.1要求美东08:00–08:30（北京夏令20:00、冬令21:00）；现有M4 `trading.execution.cli.due`固定Asia/Shanghai的20:00–20:30，不随美东DST切换。并且M4在窗口内第一次运行后按已有job guard不再重新生成；它只在生成计划时读文件，M9在盘前复核之后才发布，现有两个独立worker没有先发布覆盖层、后生成M4计划的顺序保证。

影响：冬令时M4可能先生成缺覆盖层的计划，一小时后M9才进入发布窗；夏令时也存在M4先读、覆盖层后到的时序。缺覆盖层按既有M4合同允许照常运行，但不能据此声称本应生效的当天冷静期已经进入该份计划。`handoff/M9/integration-timing.json`将用注入时钟直接复现，不调用业务或连接生产库。

需要需求方明确：M9验收的发布/消费顺序应如何与已冻结M4入口接线，以及是否另派最小调度修复统一冬令时间。倾向在运维调度层保证先完成覆盖层尝试（失败仍允许M4带缺失标记出计划），不修改M4规则、算法或订单金额。A015禁止改M4业务，故不擅自改它的窗口或绕过一次运行保护。M9自身规则、投递、影子批次和离线证据继续；受影响的是共享调度接线及其自然运行证明。
