# 协作信箱（2026-10-16 起）

需求方、A 线 agent、B 线 agent 之间只通过本仓库沟通。用户不再转发消息，只在关键节点批准。

## 1. 谁在哪条线

| 线 | agent | 范围 | 代码包 / schema |
|---|---|---|---|
| A | Codex | M3 → M4 → M5 | `inves_cog.trading`、`inves_cog.valuation_v1` |
| B | Cursor | M6 修复 → M7 → M8 | `inves_cog.perception`（含 `graph`）、`inves_cog.marketstate` |

两条线都只读 M1、M2 的数据和代码（`ingest`），不改。M6 文档里授权的几项采集例外。

## 2. 文件

| 位置 | 谁写 | 内容 |
|---|---|---|
| `ops/control.md`（main） | 用户；需求方 | 每条线的开关：`运行` 或 `暂停` |
| `ops/inbox/A/A-001.md`…（main） | 只有需求方 | 任务，一个文件一条，编号递增，发出后不改；要更正就发新编号 |
| `ops/status/A.md`、`B.md`（分支 `agent-status`） | 各线 agent，只改自己的文件 | 回报 |
| PR | 各线 agent | 交付物 |

## 3. agent 每次被唤醒时做什么

1. `git fetch origin`，读 `origin/main` 上的 `ops/control.md`。本线是"暂停"就停止，什么也不做。
2. 列出 `ops/inbox/<本线>/`，和 `agent-status` 分支上自己的 `status` 对比，找出还没回报"已完成"的最小编号任务。没有就停止。
3. 在 `status` 里写"已收到"，推送；然后按任务执行。任务里会写明依据的文档、交付物和完成标准。
4. 做完后在 `status` 里写结果，推送：`已完成`（附 PR、提交 sha、证据位置）或 `阻塞`（原因、需要谁做什么）。
5. 一次只做一条任务。做完就停，等下一次唤醒。

推送 `status` 前先 `git pull --rebase`，只改自己的文件。

## 4. status 的格式

```
## A-003  已完成  2026-10-16 15:20 北京
- PR #10，head 1a2b3c4，CI 绿
- 证据：handoff/M3/self-test.md
- 已自行决定：……（按任务书 §4.6，没有就写"无"）
- 下一步：等需求方验收
```

状态只有四种：`已收到`、`进行中`、`已完成`、`阻塞`。长任务每完成一个阶段写一行`进行中`。

## 5. 必须停下来等的情况

遇到以下任何一条，写`阻塞`并停止，不要自行处理：

- 任务书 §4.6 的"必须停"：跨模块的表结构或接口、golden、规则 A 结果或交易行为、新数据源或付费、key 或权限、不可逆删改数据；
- 要改不属于本线的代码包、schema、迁移，或改 `docs/`、`golden/`、`milestones.txt`；
- 定时服务、共用数据库的迁移（只能在合并后、按任务执行）；
- 预计比任务里写的期限晚 1 天以上。

## 6. 关键节点（用户控制）

| 节点 | 内容 |
|---|---|
| G1 开工 | 新模块的任务，需求方先给用户一页说明，用户批准后才写进信箱 |
| G2 方向确认 | 开工复述答复时，需求方向用户说明开发的理解是否偏离目标 |
| G3 验收 | 需求方出验收报告和验收页 |
| G4 合并 | 需求方把合并信息（PR、改了什么、验收结论、风险）发给用户，**用户说"合并"后由需求方合并**。agent 不合并 PR |

修复、补证据、合入最新 main 这类小任务不经过 G1，需求方直接发。
