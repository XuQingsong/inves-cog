# 协作信箱（2026-10-16 起）

需求方、A 线 agent、B 线 agent 之间只通过本仓库沟通。用户不再转发消息，只在关键节点批准。

## 1. 谁在哪条线

| 线 | agent | 范围 | 代码包 / schema |
|---|---|---|---|
| A | Codex | M3 → M4 → M5 → M9 | `inves_cog.trading`、`inves_cog.valuation_v1`、`overlay`、影子 schema |
| B | Cursor | M6 修复 → M7 → M8 → M10 | `inves_cog.perception`（含 `graph`）、`inves_cog.marketstate`、页面接口 |

两条线都只读 M1、M2 的数据和代码（`ingest`），不改。M6 文档里授权的几项采集例外。一次性例外：B-033（UD-B-06）仅可修改 `Pipeline.wide` 宽池日线拆股调整因子写入及其测试；完成该单后 B 线恢复 ingest 只读，不因此获得其他 M1 修改权。另一次性例外 B-036（UD-COORD-26）：可在 `perception` 添加 M8 PIT 快照表；仅现有 `role_perception` 写入、现有 `role_shadow` 只读读取；不新建角色、不扩到其他表。

## 1.1 一条线同时只有一个任务

每条线同时只有一个**开发任务**：**下发一个任务 → agent 执行完 → 需求方验证完 → 再下发下一个**。

- 上一个任务没有经过需求方验证，信箱里不会出现下一个编号；
- 已下发的任务文件和本 README 在任务执行期间**不改**。规则有变化，写进下一个任务的"规则变化"一节，随下一个任务生效（同一次提交更新本 README）；
- 需求方的验证结果写在下一个任务的开头。验证不通过的，下一个任务就是修复。


## 1.2 提交前自验清单（2026-10-22 起）

需求方下发任务时同时给出“提交前自验清单”（写在 `ops/answers/<任务号>.md`，接口样例放 `docs/phase1/contracts/`）。开发提交前逐项自验，在 status 的“已完成”条目按清单编号列结果、测试名和证据；需求方验收按同一清单复核。测试夹具须是真实形态（含会触发关键路径的数据），不能用空夹具让测试绕过；涉及模型调用的用计数客户端核对次数。任务约束互相冲突或做不到时先停下报告，不自行取舍。任务发出后不再修改任务文件，补充另开新编号。
## 1.2 开发验收与线上运行验证分开

- 用户决策 UD-COORD-24：**等待未来自然定时任务或数周前向数据，不阻塞下一项开发**。模块的代码/离线阻塞验收通过、PR 经需求方接受合并后，该开发任务即可结束。
- 尚未到点的自然运行、连续交易日观察、月度/20 日标签积累，作为独立的 `OPS-*` 运维验证项写入 `docs/phase1/tracker.md`，注明 owner、时间窗和证据；不占 A/B 的开发任务位，也不把它们写成已验证。
- 如果自然运行发现代码缺陷，再派一个范围明确的修复任务；如果是数据源、机器、权限或缺少真实历史数据，单列运维阻塞，开发线可以继续不依赖该阻塞的模块。
- 模块依赖的代码接口或阻塞性数据合同仍须先满足；本规则只解除“等未来自然运行才能开始下一项开发”的门槛。第一阶段最终是否合格，仍须按七场景、数据质量及用户走查结论判定。

## 2. 文件

| 位置 | 谁写 | 内容 |
|---|---|---|
| `ops/control.md`（main） | 用户；需求方 | 每条线的开关：`运行` 或 `暂停` |
| `ops/inbox/A/A-001.md`…（main） | 只有需求方 | 任务，一个文件一条，编号递增，发出后不改；要更正就发新编号 |
| `ops/status/A.md`、`B.md`（分支 `agent-status`） | 各线 agent，只改自己的文件 | 回报 |
| PR | 各线 agent | 交付物 |

## 3. agent 每次被唤醒时做什么

1. `git fetch origin`，读 `origin/main` 上的 `ops/control.md`。本线是"暂停"就停止，什么也不做。
2. 列出 `ops/inbox/<本线>/`，和 `agent-status` 分支上自己的 `status` 对比，找出还没回报"已完成"的最小编号任务。没有就停止。
3. 在 `status` 里写"已收到"，推送；然后按任务执行。任务里会写明依据的文档、交付物和完成标准。
4. 做完后在 `status` 里写结果，推送：`已完成`（附 PR、提交 sha、证据位置）或 `阻塞`（原因、需要谁做什么）。
5. 一次只做一条任务。做完就停，等下一次唤醒。可以按用户的决定定时自动唤醒（UD-A-01、UD-B-01：每 10 分钟），规则不变。

推送 `status` 前先 `git pull --rebase`，只改自己的文件。

## 4. status 的格式

```
## A-003  已完成  2026-10-16 15:20 北京
- PR #10，head 1a2b3c4，CI 绿
- 证据：handoff/M3/self-test.md
- 已自行决定：……（按任务书 §4.6，没有就写"无"）
- 下一步：等需求方验收
```

状态只有四种：`已收到`、`进行中`、`已完成`、`阻塞`。长任务每完成一个阶段写一行`进行中`。

## 4.1 向用户要的决定，必须同步

开发过程中直接问用户、用户直接给了答复的，**先写进 status 再照着做**：

```
## A-003  进行中  2026-10-16 16:40 北京
- 用户决策 UD-A-01：问题……；用户答复……；影响……（哪些文件、哪个验收条款）
```

- 编号 `UD-<线>-<序号>`，每条线递增；
- 写清问题、用户原话或要点、你打算怎么改；
- 需求方巡检时读到后，写进对应的模块文档（"已决定的问题"），或者向用户确认后改正；
- 没写进 status 的决定，需求方验收时视为没有依据的改动。

开发过程中任何影响接口、数据库结构、定时任务、数据源、依赖的变更，即使不需要停，也在 status 里写一行"变更："。

## 5. 必须停下来等的情况

遇到以下任何一条，写`阻塞`并停止，不要自行处理：

- 任务书 §4.6 的"必须停"：跨模块的表结构或接口、golden、规则 A 结果或交易行为、新数据源或付费、key 或权限、不可逆删改数据；
- 要改不属于本线的代码包、schema、迁移，或改 `docs/`、`golden/`、`milestones.txt`；
- 定时服务、共用数据库的迁移（只能在合并后、按任务执行）；
- 预计比任务里写的期限晚 1 天以上。

## 6. 关键节点（用户控制）

| 节点 | 内容 |
|---|---|
| G1 开工 | 新模块的任务，需求方先给用户一页说明，用户批准后才写进信箱 |
| G2 方向确认 | 开工复述答复时，需求方向用户说明开发的理解是否偏离目标 |
| G3 验收 | 需求方出验收报告和验收页 |
| G4 合并 | 需求方把合并信息（PR、改了什么、验收结论、风险）发给用户，**用户说"合并"后由需求方合并**。agent 不合并 PR |

修复、补证据、合入最新 main 这类小任务不经过 G1，需求方直接发。
