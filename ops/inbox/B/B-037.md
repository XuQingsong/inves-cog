## 验收发现

当前 PR #47 的 `_EVENTS` SQL 已取出 `linkage_events.mechanism`、`deadline_outcome`，但 `_row_event` 丢弃两列并把全部 `_REQUIRED` 字段重置为空；也没有从 M8 已有的 `ticker_status`、`candidates`、`tracks`、`reports`、`market_day` 取实际字段。因此即使 M8 三个阶段都成功、表中已有当前有效值，事件快照仍全标缺失/`degraded`，M9 无法利用可用的 M8 数据。

## 任务

1. 对照 M9 provider contract，逐字段检查 M8 现有表与写入路径；从已存在且在快照 cutoff 前完成的 M8 输出中提取可证明的 `lifecycle`、`mechanism`、affected tickers/exposure、direction、divergence、dimensions、next filing、systemic tag、deadline outcome 等字段及 source IDs。
2. 快照写入发生在三个必需 M8 阶段均成功结束之后。`snapshot_generated_at` 用 injected clock 的真实时间，`source_asof` 用可核实的 M8/job/source cutoff；同一 repeatable-read snapshot 中捕获字段，避免阶段间混读。
3. 仅将确实没有来源值或无法证明可见时间的字段记为 NULL + 字段级原因。不要因为某个可选字段缺失就抹掉其他字段；若 M9 必需条件仍无法证明，快照保持 `degraded/incomplete`，M9 不应把 unknown 当作“不触发”。
4. 历史日期只用原先保留的不可变/带时间来源；没有 PIT 证据的旧记录保持 incomplete。可从现有有时间戳来源严格重建的，标为 `historical_backfill` 并记录真实 backfill 生成时间，绝不伪造当时可见。
5. 确保 snapshot 真正 append-only；各事件字段与 M9 需要的状态、方向、暴露含义有明确映射，不能把异常涨跌方向冒充事件方向。
