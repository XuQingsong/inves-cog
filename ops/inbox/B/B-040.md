# B-040 B-039 验收修复：股票池结构化事件、09:30 不重复调用模型、估算与实际一致

> 发给：B 线（Cursor）。前置：B-039 已交 PR #47 head `f4f4223`（CI 442 passed）与 PR #48 head `2b6dc89`（CI 448 passed）。需求方逐行审查后**暂不验收、不合并**，问题如下；在同两个 PR 上修复。授权沿用 UD-COORD-26/27，不新增 schema、角色、数据源。

## 审查发现

1. **股票池（pool）有盘前新闻的异常不产出结构化事件。** `chain._one` 对 pool 且有 `_before_move` 新闻的异常只走 `_phase1_move`（一次 move_card 提问），`_save_move` 只保存 `report`（daily_text/move_card），不写 `linkage_events`、`ticker_status`、`claims`、`candidates`。快照从 `linkage_events` 组事件，于是这些异常没有 lifecycle/mechanism/exposure，M9 永远无法对池内股票给冷静期。M9 的核心案例（WDC/STX/MU）正是池内股票。
2. **09:30 `attribution_tracks` 会再次调用模型并覆盖 09:15 报告。** 同一 `_one` 分支条件是 `stage != "attribution_labels"`，tracks 阶段同样进入 `_phase1_move`→`move_card(client)`。`test_tracks_reads_the_saved_stage_and_does_not_call_the_model` 的夹具没有任何新闻，所以没覆盖这一路径。生产与回放都会多调用，违背“09:30/12:30 不调用模型”的 PR 说明。
3. **dry-run 估算与实际调用不一致。** `replay_window.expected_calls` 对 tracks/labels 一律 0、对 `universe=="wide"` 一律 0；但 wide 在 `_score_one` 的 else 分支每个阶段都会执行 `_claims`/`_candidates`（是否真调用模型取决于实现，须以实测为准），上面第 2 点也会在 tracks 调用。估算若偏低，A 线向用户报出的费用就是错的。
4. **PR #47 回退了 B-038 的逐标的值。** `_flatten` 的 members 分支把每只标的的 `divergence_tag`/`next_filing_at` 换成了事件级值，B-038 按标的保留的差异丢失。

## 修复要求

- **pool 结构化事件**：09:15 对 pool 异常，在生成 move_card/早页的同时，用现有 `_score_one` 完整链（claims→candidates→lifecycle→`_bundle`）落库，使 `linkage_events/ticker_status/claims/candidates/tracks/reports` 有该异常的行。move_card 与早页文字不变；早页那次提问不重复。新增模型调用只允许是完整链本身所需的调用（预计每个 pool 异常 claims 1 次、candidates 1 次，以实测为准），并在 PR 说明写清。
- **09:30/12:30 零模型调用**：tracks 阶段 pool 异常不得再进入 `_phase1_move`；走 `_score_one` 并通过现有 `_resume_analysis` 复用 09:15 分析。wide 在 tracks 阶段若当前实现会重新调用模型，改为复用 09:15 结果；不能复用则如实记录、不重复调用。labels 保持零调用。
- **估算以实测为准**：删掉手写规则式的 `expected_calls` 判断，改为用与真实运行同一代码路径、注入“只计数不调用”的客户端执行 dry-run（store 用内存、不写库）。新增测试：同一组含 pool+wide、含盘前新闻与无新闻的夹具，dry-run 计数 == 用计数客户端真实跑三阶段的调用次数，并逐阶段断言 09:30/12:30 为 0。
- **逐标的值**：恢复 members 分支逐只的 `divergence_tag`/`next_filing_at`（cutoff 晚到时仍按缺失处理），补回归测试。
- 回放（`replay_window`）随上述修改同步：pool 有结构化事件写入内存 store，快照 events 来自完整链结果。
