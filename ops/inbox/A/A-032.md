# A-032 数据守护：缺失/陈旧/异常告警 + 自动补数 + 邮件通知

> 优先级：**高于 A-031**。A-031 暂停（保留已做部分，不丢弃），A-032 交付验收后再继续 A-031。A-030 部署照常优先。
> 背景（用户 2026-11-06）：服务器卡死导致 11-05 的 VIX 陈旧（与前一日相同）、10Y/MOVE/信用利差缺失、OCC 期权成交量缺 11-05、空头成交量表整张为空、SOXX 价格 −70.7% 异常，晴雨表因此低估恐慌——系统没有任何提示，是用户问起才发现。用户要求：数据缺失必须自动被发现、自动尝试补齐，并主动通知。
> 当前一次性补数由运维另行处理（证据 `ops/swe2-backfill-20261106.txt`），本单做长期机制。
> 授权：新增 `src/inves_cog/dataguard/`、`config/data_expectations.yaml`、`scripts/`、新迁移（`ops` 或 `ingest` schema 下的新表）、新 supervisor 程序、页面“数据状态”区的展示（`src/inves_cog/web/`）、测试。可调用各采集模块现有的补采/重跑入口，不改其业务逻辑。

## 1. 数据期望清单（配置驱动）

`config/data_expectations.yaml`，每个数据集一项，至少字段：
- `dataset`、`table`、`date_column`、可选 `filter`（如 ticker 列表、series_id）；
- `cadence`：`trading_day` / `weekday` / `intraday:<分钟>` / `weekly` / `monthly`；
- `deadline_et`：日期 D 的数据最晚应在何时到位（例如日线 D 日 20:40 ET）；`grace_min`：宽限分钟；
- `min_rows` 或 `min_coverage`（相对监控池或前 5 个同类日的中位数）；
- `staleness`：对应变化的序列（VIX、10Y、MOVE、HYG、IEF、日元、黄金、比特币等），若 D 日值与前一日**完全相同**且前一日也有值，判为“陈旧”；
- `sanity`：单日涨跌幅阈值（ETF/指数 > 25%、个股 > 60%）且当日无公司行动记录 → 判为“可疑”；
- `backfill`：补数入口（现有 CLI/函数名与参数模板）、`max_attempts`、`depends_on`（补完后需重算的下游，如 11-05 VIX 补齐后重算 `barometer_daily` 该日）。
- 覆盖范围至少包括：日线（池内+宽池+SPY/QQQ/SMH/SOXX 等 ETF）、盘中快照、晴雨表全部输入序列（`flows.observations` 各 series）与 `barometer_daily/intraday`、`flows.etf_daily`、`flows.option_volume_occ`、`flows.option_chain`、`flows.short_volume`、`flows.cftc_positions`、新闻（`ingest.info_items` 交易时段 2 小时无新增）、财报/fin_state、一致预期快照、`valuation_v1.ranges`/`ceiling_daily`、规则 A 评分与纸面计划、M8 日报、`ingest.job_runs` 各定时任务的失败与缺跑。逐项从现有代码与数据核实实际的到位时间后再写 deadline，不拍脑袋。

## 2. 守护程序 `data_guard`

- 新 supervisor 程序，每 10 分钟运行一次，单进程、轻量查询（每条带 `statement_timeout`），不得做全表扫描（按日期索引查最近几日）。
- 输出写新表 `dataguard.gaps`（或同等）：`dataset, data_date, kind(missing/partial/stale/suspect/job_failed), detail(jsonb), first_detected_at, last_checked_at, attempts, last_attempt_at, status(open/backfilling/resolved/unrecoverable), resolved_at`。同一缺口只一行，状态迁移有记录。
- **自动补数**：过了 deadline+grace 的 open 缺口，按 `backfill` 配置串行尝试（同一时间最多 1 个补数进程，`nice`，子进程方式运行，遵守服务器资源纪律），每次间隔递增，超过 `max_attempts` 置为 `unrecoverable` 并说明原因（如数据源当日无数据）。补数成功后执行 `depends_on` 下游重算，再复核缺口是否消失。
- 可疑（suspect）类不自动“修正”数值，只告警并在 detail 里给出证据（前后价格、是否有拆股记录）。
- 资源保护：读取 `inves-cog-data/monitor/alerts.log` 或 slice 内存指标，若服务器处于内存/IO 告警状态，暂停补数，只记录。

## 3. 邮件通知

- 用户选择邮件。SMTP 配置从服务器环境变量读取（`INVES_SMTP_HOST/PORT/USER/PASSWORD/FROM`、`INVES_ALERT_TO`），**不得写入仓库**；变量由用户在服务器配置，未配置时守护程序照常运行，只在页面与日志显示“邮件未配置”。
- 发送规则：
  - 新缺口在过 deadline+grace 仍未补齐时发一封（同一缺口只发一次，状态变为 `unrecoverable` 或补齐时再发一次结论）；
  - 同一轮发现的多个缺口合并为一封；
  - 每天北京时间 08:30（美股收盘后、开盘前）发一封日报：昨日各数据集完整度、未解决缺口、自动补数结果、服务器资源告警摘要（来自监控 `alerts.log`）。
- 邮件为中文，写清：哪个数据、哪一天、什么问题、对哪些功能有影响（例如“晴雨表恐慌情绪维度被低估”）、系统已做了什么、需要人做什么。
- 发送失败要重试并记录，不能静默。

## 4. 页面

- “可靠性/数据状态”页显示当前未解决缺口列表（数据、日期、问题、影响、状态）；有未解决缺口时首页顶部显示一条横幅“部分数据缺失：…（详见数据状态）”。遵守页面禁用规则，缺数据明示。
- 晴雨表等依赖这些输入的页面，在对应日期有缺口时标注“该读数受数据缺失影响”。

## 5. 约束

- 不在生产跑重计算；守护程序常态内存 < 150MB，单次检查 < 30 秒，给出实测。
- 首次上线时以“只检测不补数”模式运行 1 天（配置开关），确认无误报后再开启自动补数——开关切换由需求方决定。
- 提问与推进按 `ops/README.md` §5.1。
