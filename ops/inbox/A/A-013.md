## 为什么有这张单

每天早上那一页的命令已经在主分支上：`python -m inves_cog.perception.attribution.morning`。它只在北京 09:15（美国冬令时改为北京 10:15）真正写页，其他时刻什么都不做。现有定时服务没有登记它，所以到点不会自己写。

今天北京 09:15 已经过了。10 月 19 日（周一，美国夏令时）收盘后的那一页，本该在北京 2026-10-20 09:15 写出。这一次要用那个时刻补跑，不能用「现在」去取数。补跑不是按时运行。下一次北京早上由定时自己写出的那一页，才算按时运行。

需求在 `docs/phase1/news-and-moves-phase1.md` 第 14 节和第 17 节。估值这一阶段不改，见第 16 节。

## 什么时候发生，什么时候不发生

分两段。第一段做完就停，等需求方把 PR 合并进 `origin/main`。你被再次唤醒、并且 `origin/main` 已经包含这次合并之后，再做第二段。不要在合并前动 Mac 上的服务。

### 第一段：登记，不安装

发生：新增一个常驻轮询，挂进 `scripts/install_ingest_service.py` 已经生成的那份服务配置。现有程序一个不删：`scheduler`、`daily_modules`、`financials`、`watchdog`、`embedding`，以及 Mac 上的 `awake`。

轮询脚本放在 `scripts/schedule_morning_page.py`，做法对齐 `scripts/schedule_daily_modules.py`：进程不退出，大约每 30 秒看一次钟。

- 只有当前这一分钟是早上那一页自己认定的那一分钟，才调用一次 `python -m inves_cog.perception.attribution.morning`（不带 `--at`）。钟点用现有 `job_slot`：夏令时北京 09:15，冬令时北京 10:15。不要在脚本里另写一套钟点。
- 这一天这一分钟试过之后，不论退出码是 0 还是 1，把「已经试过」记在仓库里的 `.harness/service/`（该目录不进 git）。同一分钟再轮询、进程重启，都不再调用。下一天的那一分钟再跑。
- 不在这一分钟时：不调用早上命令，不调模型，不写那一页。
- 调用前，用和现有定时任务相同的方式读取仓库根目录那个不进 git 的私有环境文件，放进进程环境。早上命令只看进程环境，不自己读这个文件。`INVES_COG_PAGE_DIR` 指到仓库外面的目录（这台 Mac 的用户目录下单独一个 `daily-pages` 即可）。服务配置文件里只保留现在这种 `PYTHONUNBUFFERED`，不要把环境文件的内容写进去。
- 日志里不打印环境文件的值，不打印那一页的正文。

不发生：不改 `src/inves_cog/perception/`，不改估值、计划、检测、新闻和波动的问法，不改 `docs/`、`golden/`、`milestones.txt`。不改表。不新建数据库角色。

### 第二段：安装，并补出一页

发生：在 A-006 那台 Mac 上，把主仓库快进到最新 `origin/main`（必须已经包含第一段的合并），用 `scripts/install_ingest_service.py --install` 重新安装并重启定时服务。密钥仍只在那份私有环境文件里。

然后补跑一次，只一次：

```bash
python -m inves_cog.perception.attribution.morning --at 2026-10-20T09:15:00+08:00
```

这一次写出的是交易日 2026-10-19 的那一页，只用 2026-10-20 09:15 北京时间已经知道的数据。跑之前如果运行记录里已经有这次补跑，不要再跑。

## 验收例子

先写会失败的例子，再改。例子不连真实数据库，不调模型。
