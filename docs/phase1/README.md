# 第一阶段开发文档 · 总览

> 依据：[`../system-spec.md`](../system-spec.md)（统一规格 v1.3）。公式、规则、参数以规格为准；范围、接口、测试、验收以本目录为准。
> 这是一个**独立项目**：代码、测试、配置、迁移全部写在本仓库 `XuQingsong/inves-cog`（`src/inves_cog/`、`tests/`、`config/`、`migrations/`），不导入、不调用 stock-pm 或 Muse 的代码，不读写它们的数据库。纸面研究，不下单。
>
> **分工**：需求方只负责需求文档和验收，不写代码；开发由开发者完成。开发不修改 `docs/` 下的任何文件，对需求的疑问通过开工复述单和 Q&A 提给需求方。

本目录做三件事：

1. **开发需求**：第一阶段拆成 M0–M10 共 11 个模块，每个模块一份文档，写清做什么、不做什么、输入输出契约。
2. **自测标准**：每个模块的验收都落到 Harness 测试或可复核的证据上，开发提交前自己跑完。
3. **验收标准**：需求方验收只按模块文档里**事先列出**的条款判定，每条条款都追溯到需求和第一阶段目标。

## 2. 流程：从开工到关闭

每个模块都走同样的六步。前两步是为了把"需求边界理解不一致"消灭在写代码之前。

| 步骤 | 谁 | 做什么 | 产出 | 不满足就不能进入下一步 |
|---|---|---|---|---|
| ① 开工复述 | 开发 | 读模块文档，用自己的话写一页复述：做什么、不做什么、输入从哪来、输出给谁、怎么验收；列出所有疑问和"文档没写、我打算这样做"的地方 | 复述单（模板见 §7.1） | —— |
| ② 澄清 | 需求方 | 逐条回复复述单；有歧义的地方写进模块文档的"已决定的问题"，文档版本号 +1 | 新版模块文档 | 复述单里的每个疑问都有书面答复 |
| ③ 开发 | 开发 | 先提交失败的测试和夹具，再写实现；中途的新疑问回到步骤 ② | 代码、测试 | 不得自行决定文档没写的行为 |
| ④ 中期检查点（M2、M4、M8） | 开发 + 需求方 | 交一份输出样例（真实数据跑一天或一个夹具），只核对契约和边界，不做验收 | 样例 JSON 和简短说明 | 契约字段和语义一致 |
| ⑤ 自测 | 开发 | 跑完本模块 Harness，逐条自评验收条款，附证据 | 自测报告（模板见 §7.2） | 本模块应关闭的不变量全部转绿 |
| ⑥ 验收 | 需求方 | 在干净环境复跑，逐条判定验收条款，出验收报告 | 验收报告（模板见 §7.3） | —— |

**需求方的验收纪律**（这是对需求方自己的约束）：

1. **只按事先列出的条款判定**。模块文档在步骤 ② 之后冻结版本号；验收用的是这个版本的条款，验收时不新增条款。
2. **文档没写的问题记为"需求缺陷"**（编号 RD-xx），写进验收报告，但**不计入本次判定**；补进下一版文档，必要时另开任务。
3. **每个"不通过"都必须给出**：条款编号、复现命令、实际结果、期望结果、对应的需求原文或规格章节。给不出这些的，不能判不通过。
4. **判定只有三档**：通过；有条件通过（只有标为"非阻塞"的条款未过，写明期限）；不通过（任一阻塞条款失败）。
5. **同一条款因为文档歧义第二次不通过**，记为需求方责任：先改文档，再重新验收，不计入开发的返工次数。

## 3. 通用约定（所有模块都必须遵守）

这一节是最容易产生分歧的地方，所以统一写死。模块文档不重复，除非有例外。

### 3.1 时间与交易日历

- 数据库里的时间戳一律存 **UTC**（`timestamptz`）；页面同时显示北京时间和美东时间。
- 交易日历用 `exchange_calendars` 的 `XNYS`，包含半日市（例如感恩节次日 13:00 收盘）。
- 业务日期 `trade_date` = 美东交易日。
- 时段划分（美东时间）：盘前 `pre` = [04:00, 09:30)；盘中 `intraday` = [09:30, 收盘)；盘后 `post` = [收盘, 20:00]；收盘一般为 16:00，半日市为 13:00。休市日发生的事件记 `closed`，归入下一个交易日。
- 夏令时切换（2026-11-01）由日历库处理，代码里不得手写 ±4 / ±5 小时。

### 3.2 时钟

- 业务代码只能通过 `inves_cog.clock.Clock` 取时间（`now_utc()`、`today_trade_date()`）。
- 生产用 `SystemClock`，测试用 `FrozenClock`。
- `src/inves_cog/` 下除 `clock.py` 外出现 `datetime.now(`、`datetime.utcnow(`、`date.today(`、`time.time(` 即失败（M0 的门禁）。

### 3.3 单位与数值

- 规格里单位为 % 或 pp 的字段，存**百分数数值**（12.5 表示 12.5%）。p、R、β、相关系数、比例上限等无单位量存小数（比例上限 25% 存 0.25）。
- 金额一律美元；股本、股数按原值存。
- 计算全程用 float64；**比较阈值前不得舍入**；只在页面显示时舍入。
- 阈值的开闭以规格符号为准：`≥`、`≤` 含等号；`>`、`<` 不含。
- 标准答案的比较容差：绝对误差 1e-6，另有说明的除外。

### 3.4 空值

- 缺数据一律存 `NULL`，JSON 输出 `null`。**不得用 0、空字符串或 NaN 代替缺失。**
- 账本为空和账本为 0 分是两回事：空表示"不能判断"，必须带健康码或原因；0 分表示"判断过了，就是最差"。
- 页面上缺失显示"数据暂缺"或健康码；未接通的数据源显示"未接通"。

### 3.5 参数与配置

- 所有阈值和参数集中在 `config/params/p-YYYY.MM.yaml`，带版本号；代码通过 `inves_cog.params` 读取，**不得在业务代码里硬编码阈值**。
- 规则 A 的 v18 常量另存 `config/params/rule_a_v18.yaml`，由 I03 校验。
- 每一条决策记录（订单、跳过、覆盖层、异常、估值行、影子记录）都带 `params_version`。
- 密钥只从环境变量读取，不进仓库、不进测试、不进日志。

### 3.11 工程基线

- Python ≥ 3.11；`pyproject.toml` 管理依赖，依赖版本锁定（`uv.lock` 或等价的锁文件）；测试框架 pytest。
- 数据库 PostgreSQL ≥ 15 + pgvector；库名 `inves_cog`。
- 测试需要数据库时，用临时数据库（docker compose 服务或测试容器），不连任何共享或生产库。
- **一条命令复跑**：`make phase1-test` 在干净机器上（只装 Docker 和 Python）完成建环境、迁移、跑 `phase1_blocking`；`make phase1-replay`、`make phase1-cases` 同理。需求方验收就用这几条命令。
- Web 框架由开发选择，开工复述里说明；页面必须有 JSON 接口（M10）。

### 3.12 任务运行记录

每个定时任务每次运行写一行 `ingest.job_runs`：任务名、`trade_date`、开始和结束时间、状态（`ok` / `degraded` / `failed`）、处理条数、错误摘要、`params_version`。页面和验收都以这张表为准，不以日志文件为准。

## 4. Harness 总则

- 层与标记：`phase1_blocking`（H0 静态门禁 + H1 纯函数，每次提交跑，3 分钟内跑完）、`phase1_replay`（v18 回放，每晚跑，改 `trading` 时也要跑）、`phase1_cases`（案例回放，改 `perception` 时跑）、`phase1_live`（真实数据冒烟，只在验收和每日任务里跑，不进 CI）。
- 测试里任何网络访问即失败；时间只能来自注入的时钟。
- `tests/harness/pending.txt`：每行 `测试名 | 模块 | 原因`。被 skip / xfail 但不在文件里 → 失败；模块已写进 `milestones.txt` 但文件里还有它的测试 → 失败。
- `tests/harness/milestones.txt`：已通过验收的模块编号。**只有验收报告结论为"通过"或"有条件通过"后才能写入**。
- `tests/harness/CHANGELOG.md`：冻结输入的每一次改动都写一条：文件、旧哈希、新哈希、原因、规格编号或 Q&A 编号。
- 每个模块文档的第 7 节列出该模块的全部测试名；测试名就是验收时复跑的清单，不能改名。

## 6. 第一阶段的目标级验收

模块逐个通过之后，还要做一次整体验收，直接对照第一阶段的六个目标（规格第 1.2 节）：

| 目标 | 整体验收方式 | 通过标准 |
|---|---|---|
| A1 感知股价异常 | 连续 5 个交易日真实运行；加东芝、OpenAI、Meta Muse、DeepSeek 四个案例回放 | 每天 08:30（北京）前产出异常清单；四个案例的异常全部被发现，层次和篮子与模块 M7 的期望一致 |
| A2 自主建立连接 | 同上四个案例 | 无需人工发起；正确候选进入前 3；每个候选都能追溯到信息 id |
| A3 基础分析 | 抽查 5 个真实异常的解释报告 | 报告字段齐全：冲击分解、影响范围、隐含幅度、跟踪清单 |
| A4 稳定估值 | 连续 5 个交易日 | 没有财报和一致预期变化的标的，三档价值日变化为 0 |
| A5 合理交易 | 连续 5 个交易日的盘前计划 | 每个动作和"不动作"都有规则编号或 N 代码；健康页没有"可买但账本为空" |
| A6 复盘补强 | 运行满 20 个交易日后 | 每个异常都有 T+1、T+5、T+20 记录；周报和漏检报告按时生成 |

外加规格第 16.9 节的完成定义。
