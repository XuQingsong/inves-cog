# M5 / M8 开发完成后的独立验收方案（Cursor 云端）

> 2026-10-17，北京时间。负责人：Cursor 云端（用户指定，只做验收，不写业务代码）。
> 依据：M5 v3、M8 v8 冻结文档；main 上的正式答复（`ops/answers/`）；[M0–M8 整体验证计划](M0-M8-validation-plan-2026-10-17.md)。
> 本方案只规定**怎么验**，不新增门槛、不改 golden、不改规则 A。

## 1. 原则

1. **用户通知后才开始**。用户告诉我哪个模块、哪个 PR 开发完成；我不自己轮询，也不在开发中途插手。
2. **只验准确版本**。开始时记下 PR head 的完整 SHA。验收期间如果又有新提交，本轮结论只对旧 SHA 有效，新提交另起一轮。
3. **只按已冻结的条款判定**。验收中发现文档本身写得不清楚，记为需求方缺陷（RD-xx），不算开发失败；不在验收时临时加条件。
4. **已验证且没变的证据直接复用**。和上一次已验 SHA 比较 diff，没改到的部分不重复跑慢测试；改到的部分要针对性重验，并补反例。
5. **不转述开发自报**。"已完成""CI 绿""passed 字段"都要自己复现。开发提供的算术结果，要用独立脚本重算，不导入被测实现。
6. **四种结论分开写**：代码验收通过、已合并、已部署、真实按时运行。不能用前一种冒充后一种。
7. **验不了就写"证据不足"**。缺数据库、缺授权时如实标注，不写成通过，也不写成失败。

## 2. 每轮验收的固定步骤

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 1 冻结 | 记下 PR、head SHA、CI run；在独立 worktree 检出这个准确提交 | 报告开头的"验收对象" |
| 2 范围 | 和上次已验 SHA 做 diff，标出改动文件；核对没有越界（`docs/`、golden、milestones、别的线的包或 schema、规则 A 参数） | 越界清单（有越界就直接退回） |
| 3 门禁 | 在干净环境顺序跑 `make phase1-test`，再跑 `phase1-replay` 或 `phase1-cases`；不同时跑两套。核对 `pending.txt` 里本模块的行；和 main 做 merge-tree，检查能否干净合并 | 通过数、失败数，以及失败是否属于环境问题 |
| 4 逐条 AC | 按第 3、4 节逐条判定，每条附证据位置 | AC 表：通过 / 不通过 / 证据不足 |
| 5 回归 | 历次验收发现过的问题逐条复测（第 3.2、4.2 节），保证已修的没有回退 | 回归表 |
| 6 报告 | 写 `docs/phase1/acceptance/<模块>-cursor-<SHA前7位>-<日期>.md`，提交推送 | 报告链接 |
| 7 结论 | 通过：给用户合并单（G4）；不通过：列出问题、最小复现和修复范围，交回原任务 | 给用户的三五行结论 |

**报告结构**：服务哪个目标 → 结论 → 逐条证据 → 开放项（标明责任方、是否阻塞）。
