# 第一阶段任务书

> 读者：第一阶段的开发 agent 和开发者。
> 先读 [`../00-overall-brief.md`](../00-overall-brief.md)（整体需求与目标），再读本文。每个开发任务有一张任务卡（`T00`–`T10`），一张卡交给一个 agent。

---

## 1. 第一阶段的目标

**一句话**：系统每天能**看见、解释、记录**市场异常，按现有规则 A 机械地运行纸面组合，并让用户看懂它做了什么、没做什么、为什么。

| # | 目标 | 怎样算达到 |
|---|---|---|
| A1 | 感知股价异常（以天为单位） | 每个交易日北京 09:15 前产出异常清单（夏令时；冬令时 10:15），覆盖标的池、广域集合和全部篮子；含盘后异动 |
| A2 | 自主建立符合逻辑的连接 | 不用人工发起；四个历史案例的正确原因进入前 3；每个候选原因都能追溯到具体信息 |
| A3 | 基础分析 | 每个异常有标准化的解释报告：冲击分解、影响范围、按渠道的隐含幅度、跟踪清单 |
| A4 | 稳定的估值 | 所有标的每天有可复算的估值区间；没有财报和一致预期变化时三档价值不变 |
| A5 | 合理的交易 | 纸面组合按规则 A 运行，复现 v18 回测；每个动作和"不动作"都有规则编号或理由代码 |
| A6 | 复盘补强 | 每个异常在 T+1、T+5、T+20 都有打标；周报、月报、漏检报告按时生成；先兆快照每天保存 |

## 2. 范围

**做**：数据采集与数据健康；财报、分部、一致预期与基本面档案；规则 A 打分与纸面执行（含 v18 复现）；估值 v1.1 与估值—仓位对照（只展示）；图谱、篮子、价格结构层；日级异常感知；建连归因与三轨跟踪；覆盖层（冷静期、撤单）；影子信号与因子候选池；页面、处置卡与复盘。

**不做**：策略回测（第二阶段）；A+ 交易规则（第二阶段）；用估值改仓位；盘中 5 分钟级异常；实盘下单；社交数据；融券费率和产业价格数据。

## 4. 开发工作规则（所有任务卡通用）

### 4.1 每个任务的六步

| 步骤 | 你要做的 | 产出位置 |
|---|---|---|
| ① 开工复述 | 读任务卡和对应模块文档，按模板写复述单：你理解的范围、不做的事、输入输出、怎样证明每条验收条款、全部疑问 | `handoff/Mx/kickoff.md`，以草稿 PR 提交 |
| ② 等待答复 | **提交复述单后停下**，等需求方答复。答复会写进模块文档的"已决定的问题"，文档版本号加一 | 需求方更新 `docs/phase1/Mx-*.md` |
| ③ 开发 | 先提交失败的测试和夹具，再写实现；中途的新疑问按 §4.6 分级：只有"必须停"的才写进 `handoff/Mx/questions.md` 并停下，其余自行按保守做法决定、记录后继续 | 代码、测试 |
| ④ 中期检查点（只有 M2、M4、M8） | 按模块文档提交输出样例 | `handoff/Mx/checkpoint.md` |
| ⑤ 自测 | 跑完本模块全部测试，逐条自评验收条款，附证据 | `handoff/Mx/self-test.md` |
| ⑥ 提交验收 | PR 转为正式，标题 `[Mx] 提交验收`；需求方在干净环境复跑并出验收报告 | 验收报告在 `docs/phase1/acceptance/Mx-report.md` |

复述单、自测报告的模板在 [`../../phase1/README.md`](../../phase1/README.md) 第 7 节。

### 4.2 分支和 PR

- 每个任务一个分支 `phase1/mx-<短名>`（例如 `phase1/m3-rule-a-scoring`），一个 PR。
- PR 只包含本任务的改动；顺手修别的模块，会被要求拆出去。
- 合并条件：`make phase1-test` 绿；验收报告结论为"通过"或"有条件通过"。

### 4.3 共享文件怎么改（避免多个 agent 互相冲突）

| 文件 | 规则 |
|---|---|
| `tests/harness/pending.txt` | 只能删除**本模块**的行；不能新增别的模块的行 |
| `tests/harness/milestones.txt` | 开发不改；验收通过后由需求方写入 |
| `tests/harness/CHANGELOG.md` | 只追加，不改历史条目 |
| `migrations/` | 文件名 `phase1_<模块>_<序号>_<说明>.sql`，例如 `phase1_m2_0001_fin_state.sql`；不改别的模块的迁移 |
| `config/params/p-2026.10/` | 每个模块一个文件，例如 `m3.yaml`；加载器合并整个目录，`params_version = p-2026.10` |
| `config/llm_tasks.yaml` | 只有 T00 能改；需要新任务名，先提给需求方 |
| `docs/` | **任何开发都不改** |

### 4.4 必须遵守

1. **只在本仓库写代码**；不导入、不调用 stock-pm 或 Muse 的代码，不读写它们的数据库。需要 Muse 的计算细节时读它的源码作参照，在本项目内重写。
2. **不改标准答案**（`docs/phase1/golden/`）。认为它错了，写进 `questions.md`。
3. **不跳过测试**；缺夹具就保持红灯，并在 `pending.txt` 写明原因。
4. **测试里不访问网络、不用系统时间、不用真实 key**；LLM 只用录音回放。唯一例外是 `phase1_live` 冒烟测试：只在显式执行 `pytest -m phase1_live` 且设置 `INVES_COG_LIVE=1` 时联网，永不进 CI。
5. **文档没写的行为不自己决定**；先问。
6. **只用两个 LLM**：`glm-5.3` 和 `deepseek-v4.1-flash`，按 `config/llm_tasks.yaml` 的分档；其他模型名不能出现在代码和配置里。
7. **缺数据就是 `NULL`**，不能用 0 或前一天的值代替。

### 4.5 被前置条件卡住时

账号、key、权限这类前置条件（模块文档 README 第 8 节的 R1–R6）还没到位时：

- 用夹具和录音把功能和测试做完；
- 依赖真实数据的 `phase1_live` 测试写进 `pending.txt`，原因写"等待 Rx"；
- 在 `handoff/Mx/self-test.md` 里列出哪些验收条款因此暂时无法证明；
- 不要为了绕过前置条件而改用别的数据源或模型。

### 4.6 效率规则（2026-10-15 起）

M1、M2 花了太多时间在对第一阶段目标价值很低的卡点上，例如为不可交易的外国标的做外币换算、为分部合计误差去解析申报原件的计算关系，等需求答复的时间也偏长。从现在起按下面的规则执行。

**1. 疑问分两级，只有第一级才停下等答复。**

| 级别 | 什么情况 | 怎么做 |
|---|---|---|
| 必须停 | 会改变跨模块的表结构或接口；会改变 golden、规则 A 的计算结果或交易行为；需要新的数据源、付费、key 或权限；不可逆地删改数据 | 写进 `questions.md`，停下等答复 |
| 不停 | 其他一切：边界情况、字段口径的细节、某个数据源的个别异常、证据怎么组织 | 选**最保守、可逆**的做法（标注缺口、不阻塞主流程、不编造数据），写进 `questions.md` 的"已自行决定"一节，继续开发。需求方巡检时确认或改正 |

**2. 单个卡点限时 1 小时。** 超过 1 小时还没解决的边角问题，用保守降级（如实标注、不阻塞）先绕过，记进 `handoff/Mx/backlog.md`（写明现象、影响、建议），回到主线。backlog 由需求方统一排期。

**3. 精度分级。** 只有以下内容要求逐字段精确：规则 A 的输入字段、v18 复现、财报反应日、按当时可见口径取数（PIT）。展示类字段、只观察的标的（外国申报人）、辅助字段，做到"正确标注缺口"即可，不做深度修复，除非模块文档明确要求。

**4. 先端到端，后打磨。** 一个模块先让主流程在真实数据上跑通，再处理边角情况。不要在一个子功能上做到极致而让主流程停着。

**5. 证据够用即可。** 每条验收条款一份最终证据；不要为同一条款保留多个版本（如 `blocking.xml`、`blocking-v3.xml`、`blocking-k16.xml`），旧版本留在 Git 历史里即可。

**6. 一个子项失败，不拖垮整个数据源。** 多个站点、关键词、代码批量处理时，逐项隔离失败、逐项记录原因。偶发失败按 M1 Q-M1-16 记为 `degraded`，只有确认不可用才记"未接通"。

### 4.7 需求冻结与模块关闭（2026-10-15 起）

M1、M2 在开发过程中补了四五轮需求，模块迟迟关不掉。从 M3、M6 起按下面的规则执行：

1. **开工前预检**：需求方在下发任务卡之前，用真实数据把需求过一遍：输入能不能拿到、案例期望在真实数据上成不成立、口径与上游的实际实现是否一致。
2. **开工后冻结**：模块文档在开工复述答复之后冻结。开发过程中发现的新问题，**只有**以下三类当场修改：数据算错；规则 A 的结果或交易行为错；安全或权限问题。其他一律进 [`tracker.md`](../../phase1/tracker.md) 的待办，放到后面的模块或下一阶段。
3. **够用就关**：阻塞验收条款通过就关闭模块。遗留项挂在 tracker 上，写明负责人和期限，不拖住模块。

## 5. 第一阶段完成的定义

同时满足才算第一阶段完成：

1. T00–T10 的验收报告结论都是"通过"或"有条件通过"，有条件项已在期限内关闭；`milestones.txt` 含 M0–M10，`pending.txt` 为空。
2. `make phase1-test`、`make phase1-replay`、`make phase1-cases` 全绿。
3. **连续 5 个交易日真实运行**：每天北京 09:15 前产出异常清单，12:30 前全部异常有归因状态，13:00 前首页完整，20:30 前发布覆盖层和盘前计划（均为夏令时下的北京时间；冬令时整体顺延 1 小时，以美东时间为准，见 README §3.1）；健康页没有"可买但账本为空"。
4. 停掉估值服务后，盘前计划与同一输入下的计划一致。
5. **运行满 20 个交易日**：每个异常都有 T+1、T+5、T+20 打标；至少 3 份周报、1 份月报。
6. 用户走查通过（M10 的 AC-M10-02）：用户能用页面回答"市场今天发生了什么、系统漏了吗、波动是基本面还是情绪、所有标的贵还是便宜、现在能不能买、风险集中在哪、系统在变好吗"。

## 6. 第一阶段结束时用户能做到什么

- 每天早上看到：昨夜哪里异常、最可能的几个原因、原因的证据和可信度、影响到哪些股票、对持仓有没有影响、接下来盯什么、什么时候有结论。
- 看到每只标的：数据是否完整、四本账、能不能买和卡在哪、估值参考（三档、位置、隐含增速）、基本面档案（分部、一致预期、季报趋势）。
- 看到盘前计划：买什么、为什么；撤了什么、为什么；没买什么、为什么。
- 看到持仓：仓位、层预算、闸门状态，以及"按估值看这个仓位合不合适"（只提示，不改订单）。
- 看到系统自己的成绩：原因未明的比例、归因的事后命中率、漏检、规则 A 和各候选因子的分歧。
